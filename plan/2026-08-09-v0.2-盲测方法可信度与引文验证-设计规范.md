# v0.2 盲测方法可信度与引文验证设计规范

**状态：** 书面规范已批准，进入 implementation planning

**日期：** 2026-08-09

**目标读者：** 项目负责人、环境经济学/政策专家、benchmark curator、工作流维护者和贡献者

**依赖基线：** v0.2 Discover + Design foundation（`master`，HEAD `005525b`）

**本规范终点：** 形成可校准的 Pilot-8 盲测包；不因此直接发布 v0.2

## 1. 目的

本规范把 v0.2 的两项 scientific release 条件转化为可执行、可审计且 fail-closed 的系统契约：

1. 独立环境经济学/政策专家认为系统在遮蔽式 held-out 问题上的方法建议可信。
2. accepted artifacts 中不存在未经验证的引文、来源性事实或定量陈述。

方法建议是否正确由独立专家依据 blinded evidence 判断，而不是由“是否复刻原论文方法”判断。原论文只在盲评分锁定后用于比较和误差分析。

## 2. 已批准的设计选择

1. **答案权威：** 采用 expert-validity 标准。原论文方法不是唯一标准答案，也不产生自动加分。
2. **遮蔽强度：** 采用 structured masking。删除论文、作者、期刊、DOI、dataset 名称和可搜索长句，同时保留方法选择必需的制度规则、变量、时间、单位和数据结构。
3. **制品架构：** 采用分离且不可变的 curator source sheet、blinded brief、leakage report、method recommendation 和 expert score sheet。
4. **验证边界：** Pilot-8 仅使用 Tier 1 metadata 与合法可读全文；不下载数据、代码或 replication package。
5. **发布边界：** Pilot-8 用于 rubric 校准。正式退出评测至少需要 16 个 held-out cases，每个内置方法家族至少两个。

## 3. 范围与非目标

### 3.1 本期范围

- 为 benchmark source、遮蔽输入、leakage 检查、方法建议、专家评分和 claim verification 定义类型化制品。
- 为 curator、masker、leakage validator、recommender、expert 和 adjudicator 定义独立 capability。
- 将所有制品绑定到精确 source generation、配置、method profile、rubric 和 producer principal。
- 离线运行 recommendation worker，使其无法访问 Zotero、互联网、source sheet 或原论文。
- 聚合双专家评分，检测分歧并路由第三位 adjudicator。
- 生成 Pilot-8 校准包和 v0.2 release-readiness report。

### 3.2 非目标

- 下载或执行 replication package。
- 获取或分析真实研究数据。
- 执行估计、复现论文结果或撰写论文正文。
- 把发表方法当作唯一 gold answer。
- 以 Agent 替代独立领域专家。
- 仅凭 Pilot-8 宣布 v0.2 scientific release。

## 4. 制品架构

每个 benchmark case 必须产生以下五类不可变制品，并通过 exact artifact references 与 content digests 串联。

| 制品 | 可见角色 | 单一职责 |
|---|---|---|
| `curator-source-sheet.yaml` | curator、post-score adjudicator | 保存完整来源身份、verified claims、原方法和原结果 |
| `blinded-brief.yaml` | masker、leakage validator、recommender、expert | 保存方法选择所需但不可反查论文的事实 |
| `leakage-report.yaml` | leakage validator、orchestrator | 证明 brief 通过身份、方法、结果、措辞和 metadata 泄漏检查 |
| `method-recommendation.yaml` | recommender、expert、adjudicator | 保存候选排序、选择/拒绝理由、假设、诊断和稳健性方案 |
| `expert-score-sheet.yaml` | 单个 expert、adjudicator | 保存独立盲评分、Critical findings 和签名 verdict |

盲评分锁定后，可生成只读的 `posthoc-comparison.yaml`。它解释建议与原论文方法的差异，但不得修改已锁定的 blind score。

## 5. 最小制品契约

### 5.1 `curator-source-sheet.yaml`

必需字段：

- `case_id`
- Zotero parent/attachment keys
- DOI 或 persistent identifier
- bibliographic identity
- source attachment hash 与 generation
- institutional context
- original method、estimand、data structure 和 findings
- verified claim entries 与 locators
- curator principal、created_at 和 schema version

该制品不得进入 recommender workspace。

### 5.2 `blinded-brief.yaml`

必需字段：

- opaque `case_id` 与 brief version
- policy/exposure setting 的非识别性描述
- unit、population、treatment/exposure timing 与 candidate outcomes
- 可用数据结构、coverage、variables、institutional rules 和真实约束
- blinded `fact_id` 列表
- 明确的 missing/unknown facts
- masker principal、source-sheet ref 和 schema version

禁止字段或内容：

- 作者、标题、期刊、DOI、URL、Zotero key 和 citation key
- dataset、project、program 或地点的可搜索专有名称，除非制度识别无法在不暴露身份的情况下成立
- 原论文 method label、规格、结果方向、显著性或结论
- 来自原文的 distinctive quotation 或长 n-gram
- 文件名、PDF metadata、hidden comments 或 provenance side channel

### 5.3 `leakage-report.yaml`

必需记录：

- source-sheet 和 brief 的 exact refs/digests
- identity、citation、dataset、method、result、phrase 和 hidden-metadata 检查结果
- 每项 finding 的 severity、locator 和 disposition
- validator principal、tool/config digests 和 timestamp
- `PASS` 或 `REJECTED` verdict

任何未关闭 finding 都使 brief 不能进入推荐阶段。

### 5.4 `method-recommendation.yaml`

必需字段：

- exact blinded-brief、leakage-report、method-profile registry 与 runtime refs
- estimand interpretation
- retained methods 的排序、compatibility evidence 和 required assumptions
- rejected methods 的结构化 unmet requirement sets
- preferred design、diagnostics、falsification、robustness 和 sensitivity plan
- data gaps、决策边界和不可识别部分
- 使用的 blinded `fact_id`
- recommender principal、runtime configuration 和 timestamp

不同于发表方法不是错误。不可行、无法识别或过度因果化的建议才构成方法缺陷。

### 5.5 `expert-score-sheet.yaml`

必需字段：

- frozen brief 和 recommendation refs
- rubric version
- 五维独立评分与书面理由
- Critical findings
- pass/fail verdict
- expert principal、签名和 locked_at
- 是否需要 adjudication

锁定后不得编辑；修订必须产生新 version，并保留原始版本。

## 6. Case lifecycle

1. **Source ingestion：** curator 解析精确 Zotero item/attachment，记录 hashes，并验证全文可读。
2. **Evidence extraction：** 将制度、数据和识别事实拆成带 locator 的 claim entries；未验证事实不得继续。
3. **Masking：** 独立 masker 仅从 verified claims 生成 method-neutral brief。
4. **Leakage validation：** 独立 validator 对 source sheet 与 brief 做对照检查。
5. **Brief freezing：** 通过的 brief 绑定 exact versions、digests、profiles、runtime 和 rubric。
6. **Agent recommendation：** recommender 在无 connector、无网络、无 source identity 的 workspace 中运行。
7. **Blind expert scoring：** 两位专家分别评分，彼此不可见；评分在 unblinding 前锁定。
8. **Adjudication：** verdict 冲突、core score 相差超过 1 分或出现 Critical finding 时，由第三位专家裁决。
9. **Post-hoc comparison：** 锁定评分后才可揭示论文，并分类记录 defensible alternative、omission 或 substantive error。

## 7. 角色与信任边界

| 角色 | 允许 | 禁止 |
|---|---|---|
| curator | 读取 Zotero 和原文；生成 source sheet | 生成或批准 blind recommendation |
| masker | 读取 verified source claims；生成 brief | 评分或批准自己的 brief |
| leakage validator | 对照 source/brief 并签发报告 | 修改 brief 或推荐方法 |
| recommender | 读取通过的 brief 和 method profiles | 访问 Zotero、网络、source sheet 或原文 |
| expert | 读取 frozen brief/recommendation 并独立评分 | 在锁分前查看论文身份或其他专家评分 |
| adjudicator | 在触发条件后独立裁决；锁分后做比较 | 覆盖或删除原始 expert scores |

任何 principal 不得生产并批准同一制品。capability 由 orchestrator 分配，不能由 worker 自报。

## 8. Expert rubric

每个维度按 0–4 分评定。

| 维度 | 权重 |
|---|---:|
| Estimand 与 identification fit | 30% |
| Assumptions、threats 与 failure conditions | 25% |
| Data compatibility 与 feasibility | 20% |
| Alternative methods 的保留/拒绝质量 | 15% |
| Diagnostics、robustness 与 policy interpretation | 10% |

单 case 通过条件：

- 加权分数至少 3.0/4.0。
- identification fit 至少 3/4。
- 无 Critical error，例如把描述性变动写成因果、忽略无效 instrument、或在没有可辩护 threshold 时推荐 RDD。
- recommendation 使用的每个事实均解析到 current verified blinded fact。

前三个维度（identification fit、assumptions/threats、data compatibility）属于 core dimensions。两位专家 verdict 不一致、任一 core dimension 相差超过 1 分或出现 Critical finding 时，必须进入第三方 adjudication。

不触发 adjudication 时，两个 score sheets 的维度算术平均值构成 case score；两位专家都必须给出 pass verdict。触发 adjudication 时，第三位专家先在看不到论文身份和既有评分的情况下独立评分并锁定，随后才能读取分歧理由并签发 final adjudication verdict。原始三份评分均保留且不可改写。未解决的 adjudication 不计入发布通过数。

## 9. Claim-level citation verification ledger

每个来源性事实必须具有：

- `claim_id`
- normalized claim
- Zotero item/attachment keys
- DOI/persistent identifier
- source content hash 与 generation
- page/section/table/paragraph locator
- supporting-passage hash
- extractor 与独立 verifier principals
- verification timestamp
- downstream artifact refs

状态仅允许：

- `UNVERIFIED`
- `METADATA_VERIFIED`
- `CLAIM_VERIFIED`
- `REJECTED`
- `STALE`

只有 `CLAIM_VERIFIED` 可以支持 accepted artifact。`METADATA_VERIFIED` 仅证明来源身份，不证明某项 claim 得到支持。

masker 将 curator-facing `claim_id` 映射为 blind `fact_id`。映射留在 curator trust boundary。完整审计链为：

```text
recommendation -> blinded fact -> verified source claim -> exact source generation
```

Final Gate 必须扫描 citation、DOI、author-year reference、定量陈述和 externally sourced factual claim。任何项目无法解析到 current `CLAIM_VERIFIED` entry 时，gate 必须拒绝而非警告。

## 10. 失败、修订与恢复

- 缺少可读全文或来源身份未解析：case `INELIGIBLE`。
- source fact 未验证：不得进入 brief。
- leakage finding 未关闭：brief `REJECTED`，case 回到 masking。
- recommender 尝试外部访问：run `INVALID`，不得评分。
- source attachment、source sheet、brief、profile 或 rubric generation 变化：所有 descendants 立即 `STALE`。
- expert conflict 未裁决：case `UNRESOLVED`，不得贡献 release threshold。
- journal、history 或 principal integrity 验证失败：恢复 fail closed。

修订只重算受影响 descendants，不覆盖旧版本。scheduler 必须拒绝指向 stale lineage 的旧 work orders。

## 11. 与现有系统集成

- 复用 v0.1 benchmark registry、run/status、journal、gate、checkpoint 和 recovery machinery。
- 复用 v0.2 Artifact DAG、method-profile registry、structured rejection evidence、trusted principals 和 semantic validators。
- 不创建第二套 runner、审批系统或来源数据库。
- Zotero 仍是默认 connector，但 authoritative benchmark state 是本地版本化 artifacts。
- benchmark recommendation 模式必须保持 Tier 1；Tier 2 registry entries 和 replication execution 在本规范范围内继续被拒绝。

## 12. 验证策略

### 12.1 Unit/contract tests

- 五类制品 schema、provenance、content digest 和 exact-ref validation。
- principal/capability separation 与 impersonation rejection。
- claim ledger state transitions、self-verification rejection 和 stale invalidation。
- scoring、disagreement detection、adjudication routing 和 threshold aggregation。

### 12.2 Adversarial leakage tests

- title、author、DOI 及编码/分隔变体。
- dataset、program、project 和地点专名。
- distinctive n-grams、近似改写和原文长句。
- method label、规格细节、结果方向、显著性和结论。
- filename、front matter、comments、PDF metadata 和 provenance side channels。

### 12.3 Integration/recovery tests

- recommender 对 Zotero、互联网和 source sheet 的访问尝试必须失败。
- 完整 Pilot-8 offline replay。
- source revision 后 descendant invalidation、re-mask、re-score 和 renewed gate。
- forged ledger、stale brief、replaced score sheet 和 cross-case artifact substitution。
- 现有 v0.1/v0.2 tests 不得回归。

## 14. v0.2 scientific release thresholds

只有同时满足以下条件，v0.2 才能从 release candidate 晋升为 released：

1. 至少 16 个 held-out cases，八个方法家族各至少 2 个。
2. 至少 14/16 cases 通过单-case 门槛。
3. 每个方法家族至少 1 个 case 通过，且家族平均分至少 3.0/4.0。
4. 零 confirmed leakage incidents。
5. accepted artifacts 中零 unverified citation 或 unsupported sourced claim。
6. 零 unresolved adjudications。
7. 全部制品 lineage、principal、journal、recovery 与 boundary checks 通过。

方法可信度门与 citation integrity 门相互独立，不能用一项高分补偿另一项失败。

## 15. 交付顺序

1. 实现并验证 artifact schemas、role capabilities、lineage 和 ledger。
2. 实现 masking、leakage scan、offline recommendation 和 scoring pipeline。
3. 生成 Pilot-8 curator source sheets、blinded briefs、leakage reports、recommendation fixtures 和 expert score templates。
4. 运行内部 adversarial replay 并校准 rubric。
5. 项目负责人人工检查 Pilot-8 校准包。
6. 扩展并冻结 16-case held-out corpus。
7. 组织独立专家盲评并生成 release-readiness report。

在第 6 步之前，若需要真实 published replication packages 验证 v0.3 方法 adapters，必须另行通知项目负责人并获得批准；该工作不属于本规范。
