# v0.2 研究工作流编排（Discover + Design）设计规范

**状态：** 五个设计章节均已批准，等待书面规范审阅

**日期：** 2026-08-05

**目标读者：** 项目负责人、研究方法审阅者、工作流维护者和贡献者

**依赖基线：** v0.1 Research Kernel and Replay Benchmark Harness（merge commit `c3600aa`）

**本期终点：** 经人工最终审批的 `analysis-plan.yaml`

## 1. 目的

v0.2 在 v0.1 可审计、可恢复的研究内核之上，建立面向环境经济学和环境政策的 Discover + Design 工作流。系统应把自由主题或结构化研究简报推进为一套有证据、有数据可行性判断、有明确 estimand、有方法筛选理由并经过独立批评的研究设计。

目标分工约为 90% Agent 执行和 10% 人工高杠杆审批。该比例描述工作投入，不转移作者、数据使用者或研究负责人的学术责任。

v0.2 设计成通用工作流，不复刻某一篇毕业论文，也不把方法限制为 DID。现有论文与将来选择的开放论文仅作为测试和演进基准。

## 2. 范围与非目标

### 2.1 本期范围

v0.2 必须支持：

1. 自由主题和结构化 research brief 两类入口。
2. 三个候选 research charters 的生成、解释、排序和人工选择。
3. connector-neutral 的文献映射，Zotero 作为默认 connector。
4. 数据可行性审计和受预算约束的 progressive acquisition。
5. estimand 规范、方法候选排序、识别备忘录和独立设计批评。
6. 两个强制人工 gate 和一个按数据风险触发的条件 gate。
7. 类型化、版本化、可追溯的 Artifact DAG。
8. 从 checkpoint 恢复并只重算受影响的 DAG 分支。
9. 八类内置 methodology planning profiles 及稳定扩展契约。
10. 生成并批准 `analysis-plan.yaml`，随后停止。

### 2.2 非目标

v0.2 不会：

- 执行计量估计、清洗完整研究数据、生成实证结果或撰写完整论文。
- 实现任何方法的 estimator code。
- 绕过付费墙、登录、许可证、隐私保护、API 条款或机构审批。
- 自动购买数据、联系数据所有者、提交论文或公开研究结果。
- 把 synthetic data 当作真实实证证据。
- 声称已达到论文级复现，或发布不同方法/Agent 的真实论文复现排名。
- 把 Zotero、ICPSR、单一模型供应商或单一 Agent runtime 变成强制依赖。

## 3. 已批准的架构选择

系统采用 **Artifact DAG over V0.1 kernel**。

- DAG 节点消费不可变、带版本的输入制品，并产出候选制品。
- Agent 是可替换 worker，不拥有权威状态。
- v0.1 kernel 负责依赖解析、状态转换、gate、重试、checkpoint、恢复、审计和预算执行。
- 对话历史只用于解释，不作为研究事实、决策或任务交接的 source of truth。
- Zotero、公共数据 API 和本地文件均通过 connector 接入；connector 的返回值必须先规范化为本地制品。
- 方法 profile 负责规划与审查，不执行估计。
- 失败返回到产生问题的上游制品；不默认重启整条工作流。

端到端主路径为：

```text
自由主题 / structured brief
  -> candidate-charters.json
  -> Gate 1
  -> research-charter.yaml
  -> [literature mapping || data feasibility]
  -> estimand-spec.yaml
  -> method-candidates.json
  -> identification-memo.md
  -> independent design review
  -> analysis-plan.yaml
  -> Final Gate
  -> approved analysis-plan.yaml（停止）
```

## 4. 核心组件

| 组件 | 单一职责 | 主要依赖 |
|---|---|---|
| `ResearchIntake` | 规范化入口并生成三个候选 charters | 输入 Schema、ranking policy |
| `ArtifactGraph` | 定义制品类型、版本、依赖和失效关系 | v0.1 state/event model |
| `ResearchOrchestrator` | 调度节点、执行 gate、重试、恢复和审计 | v0.1 kernel、ArtifactGraph |
| `ConnectorGateway` | 规范化 Zotero、文献与数据源操作及 receipt | connector contracts、预算策略 |
| `MethodProfileRegistry` | 注册、解析和验证方法 planning profiles | pack registry |
| `IndependentDesignReview` | 生成结构化设计问题，不直接修改生产者制品 | review policy、artifact validators |
| `GateService` | 管理 Gate 1、条件数据 gate 和 Final Gate | v0.1 gate machinery |

内部实现可以替换，但组件公开契约、输入输出类型和失败语义必须保持兼容。

## 5. 权威制品契约

### 5.1 继承的控制制品

v0.2 继续使用 v0.1 的 `run-manifest.yaml`、`events.jsonl`、checkpoint、finding 和 gate decision。`events.jsonl` 记录内核运行事件；`decision-log.jsonl` 专门保存研究决策及其理由，两者不得互相替代。

### 5.2 新增研究制品

| 制品 | 必需性 | 作用 |
|---|---|---|
| `research-brief.yaml` | 必需 | 保存规范化后的入口与用户约束 |
| `candidate-charters.json` | 自由主题入口必需 | 保存三个候选方向、评分、证据和排序理由 |
| `research-charter.yaml` | 必需 | 保存 Gate 1 批准的问题、范围、贡献、伦理和约束 |
| `literature-map.json` | 必需 | 保存来源、主题、方法、关系和覆盖缺口 |
| `evidence-matrix.csv` | 必需 | 按来源记录问题、数据、方法、发现、局限和相关性 |
| `data-feasibility.yaml` | 必需 | 记录候选数据的访问、许可、变量、覆盖、成本和风险 |
| `data-provenance.yaml` | 条件必需 | 仅在实际获取数据后记录来源、receipt、哈希和许可证 |
| `estimand-spec.yaml` | 必需 | 定义总体、处理/暴露、结果、对比和时间范围 |
| `method-candidates.json` | 必需 | 排序兼容方法并记录不兼容和拒绝理由 |
| `identification-memo.md` | 必需 | 论证识别逻辑、关键假设、威胁和替代设计 |
| `design-review-findings.json` | 必需 | 保存独立批评、严重级别、证据和关闭条件 |
| `analysis-plan.yaml` | 必需 | 汇总经验证的最终研究设计 |
| `decision-log.jsonl` | 必需 | 保存人工选择、Agent 分歧、修订和审批理由 |

### 5.3 通用 metadata envelope

除 CSV 外，每个权威制品必须直接包含以下字段；CSV 使用同名 sidecar metadata：

- `schema_version`
- `artifact_id`
- `artifact_version`
- `run_id`
- `created_at`（带时区的 UTC ISO 8601）
- `producer`（Agent/组件、model/runtime 和版本）
- `input_artifacts`（artifact ID、版本和内容哈希）
- `provenance`
- `validation_status`
- `content_hash`

`identification-memo.md` 必须使用结构化 front matter 携带相同 metadata。制品一经验证便不可原地覆盖；修订生成新版本，旧版本变为 `superseded`。

### 5.4 候选 charter 排序

自由主题必须产生恰好三个通过 Schema 验证且实质不同的候选 charter。每个候选对以下六项分别给出 0–100 分、证据和不确定性：

- contribution potential
- literature gap
- data feasibility
- identification plausibility
- policy relevance
- scope manageability

默认排序为六项等权平均。run manifest 可以覆盖权重，但权重必须版本化、总和为 1 且在 Gate 1 前可见。若无法形成三个有效候选，run 进入 `blocked: insufficient-candidate-diversity`，不得用近义改写填满名额。

## 6. Agent 拓扑与数据流

### 6.1 生产者角色

| Agent 角色 | 输入 | 输出 |
|---|---|---|
| `ResearchFramer` | topic/brief、约束、ranking policy | research brief、candidate charters |
| `LiteratureCartographer` | approved charter、connector receipts | literature map、evidence matrix |
| `DataScout` | approved charter、literature signals、acquisition policy | data feasibility、可选 data provenance |
| `EstimandDesigner` | charter、literature、data feasibility | estimand spec |
| `MethodStrategist` | estimand、data structure、profile registry | method candidates、draft identification memo |
| `IndependentDesignCritic` | 所有已验证设计制品 | design review findings |
| `AnalysisPlanComposer` | 关闭后的 findings 与已验证制品 | analysis plan candidate |

### 6.2 调度规则

1. `ResearchFramer` 完成后暂停在 Gate 1。
2. Gate 1 只能选择一个候选或全部拒绝；选择结果生成新的 `research-charter.yaml`。
3. 文献映射和数据可行性在 Gate 1 后并行执行。
4. 两个分支均达到 `validated` 或允许的 degraded 状态后，才能定义 estimand。
5. 方法排序必须晚于 estimand，不得先选 DID 再倒推研究问题。
6. 独立批评在 analysis plan 组装前运行。
7. 开放的 `blocking` finding 阻止 plan 组装和 Final Gate，直至关闭。
8. 开放的 `major` finding 可以随 plan 进入 Final Gate，但必须被关闭，或由人类明确接受残余风险。
9. finding 指向具体 artifact/version；修订只使该制品及其下游失效。
10. Final Gate 批准后，`analysis-plan.yaml` 进入 `approved`，v0.2 run 结束。

### 6.3 独立性约束

设计批评者使用独立运行上下文，不能读取生产者的隐藏推理，也不能审批自己的建议。可配置不同 model/provider，但 v0.2 不强制依赖第二供应商。审阅者只生成 findings；修订必须由对应生产者创建新制品版本。

## 7. 人工审批门

### Gate 1：Research Charter

**触发：** 三个候选 charters 已验证。

**人工动作：** 选择一个、要求修订或全部拒绝。

**批准内容：** 研究问题、范围、预期贡献、伦理边界、政策相关性和主要约束。

### Conditional Data Gate

当任一候选数据存在以下情况时触发：

- restricted、private 或含敏感信息；
- 需要付费或产生非零外部成本；
- 许可证未知、冲突或不允许计划中的使用；
- 预计下载、存储、API cost/calls 或 elapsed time 超过本次 run 的预算。

该 gate 可以批准继续把数据纳入设计、批准在既有合法权限下受控获取，或要求换用数据。批准不会提供权限、凭据或许可证，也不能覆盖 connector 和安全策略。v0.2 默认不自动获取受限数据；没有明确合法权限时保持 feasibility-only。

### Final Gate：Research Design

**触发：** estimand、method candidates、identification memo、review findings 和 analysis plan 均已验证，且无开放的 `blocking` finding；开放的 `major` finding 必须附带清晰的残余风险说明。

**人工动作：** 批准、明确接受 `major` 残余风险、要求局部修订或拒绝。

**批准内容：** estimand、主方法与备选方法、识别假设、诊断、排除规则、稳健性计划、数据边界和停止规则。

所有 gate 决策必须记录 decision、actor、timestamp、artifact versions、reason 和 conditions。不得通过 CLI 参数、Agent 输出或异常恢复绕过 gate。

## 8. 文献与数据策略

### 8.1 文献层

- Zotero 是默认 connector，但不是内核依赖。
- connector 输出必须转换为带 provenance 的本地记录。
- `literature-map.json` 和 `evidence-matrix.csv` 是 Agent 交接的 source of truth。
- 每项文献性判断必须指向来源记录；无法验证的来源标记为不确定，不得补造引文。
- connector 不可用时，可使用本地导出或其他合规 connector 继续；失败必须显式记录覆盖损失。

### 8.2 Progressive acquisition

Data Scout 首先检查 metadata、documentation、codebook、license、schema、API availability 和预计资源消耗。只有同时满足以下条件时，系统才可自动获取完整数据：

1. 数据公开可访问；
2. 许可证清晰且允许计划中的使用；
3. 来源和版本可验证；
4. 预计与实际消耗均处于本次 run 的预算内；
5. connector 能生成完整 acquisition receipt 和哈希。

若获取失败或数据不合适，系统退回 planning-only，不阻塞其他设计活动。每次 run 的预算至少包含：

- `max_download_bytes`
- `max_local_storage_bytes`
- `max_api_calls`
- `max_external_cost`
- `max_elapsed_seconds`

不存在隐式全局无限预算。预算调整属于有审计记录的决策。

## 9. Methodology Planning Profiles

v0.2 内置八类 planning profiles：

1. RCT
2. DiD / event study
3. RDD
4. IV
5. Synthetic Control
6. Hedonic valuation
7. descriptive / spatiotemporal environmental measurement
8. systematic review / Meta-analysis

每个 profile 必须声明：

- `profile_id`、`version` 和 method family；
- compatible estimand types；
- required data structure 与最小变异；
- identifying assumptions；
- incompatibility rules；
- mandatory diagnostics；
- common threats 与 falsification checks；
- fallback/alternative designs；
- analysis-plan template fields；
- references to methodological guidance。

`MethodStrategist` 必须保留候选方法、排序理由和拒绝理由。新增 discrete choice、contingent valuation、spatial econometrics、forecasting、structural models、CGE 或 IAM 时使用相同扩展契约，不修改 kernel。v0.2 profile 不得包含 estimator execution。

## 10. 状态、失败与恢复

### 10.1 制品状态

主状态路径为：

```text
pending -> running -> produced -> validated -> approved
```

替代终态为 `blocked`、`failed` 和 `superseded`。非 gate 制品的 `approved` 表示已被下游接受；gate 制品只有在相应人工决策后才能进入 `approved`。

### 10.2 失败分类

| 失败类型 | 处置 |
|---|---|
| 瞬时 connector/runtime 失败 | 有上限地重试；随后换 connector 或进入 degraded planning-only |
| Schema/contract 失败 | 拒绝候选输出，仅重跑生产节点 |
| 证据不足 | 记录不确定性并创建定向证据任务，不得生成支持性事实 |
| 数据不可得 | 保留 feasibility 结果，不获取数据继续规划 |
| 数据权限、成本、隐私、许可或预算问题 | 停止获取并触发 Conditional Data Gate |
| 设计矛盾 | 使受影响制品及下游失效并局部重算 |
| 人工拒绝 | 保留被拒版本和理由，创建新 revision |

每个节点必须幂等：相同输入哈希和配置不得产生第二份互相冲突的权威状态。checkpoint 恢复必须跳过仍然有效的已完成节点。重试次数、退避策略和最终处置写入 run manifest 与 event log。

## 11. 研究治理

1. 每项主张必须追溯到 literature map、evidence matrix、data documentation 或明确标记的研究假设。
2. 只有 estimand 和识别条件支持时，才能使用因果语言。
3. 不得绕过许可证、隐私、访问控制、API 限制或伦理要求。
4. audit trail 记录 Agent、model、runtime、connector、配置、输入输出哈希和验证结果。
5. Agent 分歧必须可见；系统不得静默平均为虚假共识。
6. findings 的严重级别固定为 `blocking`、`major`、`minor`、`advisory`。
7. `blocking` 必须关闭；`major` 必须关闭或由人类在 Final Gate 明确接受残余风险；`minor` 和 `advisory` 可带入计划并记录。
8. 零结果、不利结果和不可行结论均为有效输出；不得为获得显著性而改变设计。
9. 生产组件不能自行修改或晋级；变更必须经过版本化 benchmark 回归和维护者批准。
10. v0.2 在 Final Gate 后停止；进入 Execute 阶段需要 v0.3。

## 12. 测试与持续演进基准

### 12.1 测试层

- **Schema tests：** 覆盖每种合法制品及缺字段、坏哈希、坏版本、断裂 provenance 等反例。
- **DAG tests：** 覆盖依赖顺序、并行分支、局部失效、重试、checkpoint 和恢复。
- **Connector contract tests：** 使用本地/fake connectors；单元和 CI 测试不访问网络。
- **Method profile tests：** 每个内置 profile 至少有一个兼容案例和一个不兼容反例。
- **Governance tests：** 验证 gate、license、privacy 和 acquisition budget 无法绕过。
- **End-to-end tests：** 分别覆盖自由主题与 structured brief，并覆盖正常、degraded、条件 gate 和设计返工路径。
- **Research-quality evaluation：** 评估 contribution clarity、evidence coverage、data feasibility、estimand precision、identification credibility 和 uncertainty disclosure。

研究质量 rubric 每项使用 1–5 分。受控 benchmark run 必须每项至少 3 分，且不存在开放的 `blocking` finding；分数用于回归与诊断，不宣称等同于发表质量。

### 12.2 Benchmark tiers

| Tier | 内容 | v0.2 用途 |
|---|---|---|
| Tier 0 | 小型、确定性的 synthetic fixtures | CI、状态机、契约和回归测试 |
| Tier 1 | 开放获取的已发表论文设计与公开说明 | 比较研究逻辑和制品完整性，不执行原始数据 |
| Tier 2 | 许可证清晰的真实 replication packages | 留待 v0.3 验证方法 adapter 和实证执行 |

benchmark registry 必须版本化；每次真实失败都应沉淀为可重放回归案例。公共测试和隐藏测试可以并存，但评分规则、版本和输入边界必须有审计记录。

**真实 replication package 触发点：** 只有在开始验证 estimator/method adapters、声称论文级复现或发布真实复现比较分数前，Tier 2 才成为必要条件。选择、下载或执行任何 Tier 2 package 前，必须通知项目负责人并获得明确批准。ICPSR 不是 v0.2 依赖。

## 13. V0.2 验收标准

以下条件必须全部满足：

1. 两类入口均能产生合法候选或明确的结构化阻塞原因。
2. 自由主题在进入 Gate 1 前产生恰好三个可区分、可解释、可拒绝的候选 charters。
3. 两个强制 gate 和条件 gate 在所有正常、恢复和 CLI 路径中均不可绕过。
4. 每个权威制品通过 Schema、hash 和 provenance 验证。
5. 八个内置 methodology profiles 均能识别兼容案例并拒绝反例。
6. Zotero 或数据源失败时能够安全退回 connector-neutral planning-only。
7. 独立批评中的开放 `blocking` finding 能阻止 Final Gate。
8. 受影响 DAG 分支可以局部失效和重算；有效分支不重复执行。
9. 中断后的 run 可以从 checkpoint 恢复，且 event/decision logs 连续可审计。
10. 系统产出经批准的 `analysis-plan.yaml` 后停止，不执行实证分析。
11. CI 仅使用仓库自有 fixtures，不登录、下载或运行 ICPSR/外部 replication packages。
12. 系统不作论文级复现、发表质量或统计显著性保证。

## 14. 实施边界与后续版本

v0.2 实施计划应拆为四个可独立验证的增量：

1. Artifact schemas、graph 和 state integration。
2. Research intake、gates 和 connector contracts。
3. Literature/data/estimand/method planning nodes 与独立 review。
4. End-to-end orchestration、fixtures、quality rubric 和文档。

v0.3 才进入 Execute：数据转换、方法 adapters、诊断、结果注册和真实 replication packages。后续版本再加入 claim-evidence ledger、argument map、章节写作、论文保障和发布工作流。

本规范批准的是 v0.2 的科学与系统边界，不授权下载外部受限材料、执行真实论文复现包或开始实证分析。
