# V0.3-A Useful Release: Trusted Local DiD Analysis

**Status:** Approved
**Date:** 2026-08-11
**Product rule:** finish a useful DiD workflow before expanding methods; reuse one
small econometrics runtime for later method bundles.

## 1. Decision

V0.3-A will finish as a trusted local-data DiD/event-study analysis capability.
It will not execute arbitrary author code or a real external replication package.

The Baker et al. (2026) JEL record remains a non-executable `proposed` benchmark.
External package admission, download, and container execution remain fail-closed
until a later local Unix-socket container broker and per-run incremental evidence
meter are separately designed and approved.

This separates two different security problems:

1. **Trusted local analysis:** Research OS generates and executes its own reviewed R
   scripts against a user-selected local dataset.
2. **Untrusted package replication:** Research OS executes third-party author code.
   This stays disabled in V0.3-A.

## 2. Goals

V0.3-A must provide a practically useful DiD workflow that:

- accepts a local dataset and explicit column mapping;
- never modifies the original dataset;
- runs a TWFE baseline and Callaway--Sant'Anna group-time ATT analysis;
- produces dynamic/event-study aggregation and explicit confidence intervals;
- checks treatment timing, comparison support, balance, and pre-treatment evidence;
- emits validated tables, figures, diagnostics, configuration, and provenance;
- completes green runs autonomously and returns typed evidence on failure;
- preserves all V0.2 planning-only and Tier-2 rejection boundaries.

## 3. Non-goals

V0.3-A will not:

- download or run the JEL replication package;
- execute user-authored or paper-author-authored R scripts;
- install R packages or contact a package repository;
- provide a hostile-code sandbox;
- support arbitrary container engines or remote container endpoints;
- add RDD, IV, Synthetic Control, Hedonic, or Meta-analysis execution yet;
- claim paper-level replication from local synthetic or user data.

## 4. Architecture

The local analysis lane is independent from the existing external replication
lane.

```text
LocalAnalysisSpec
  -> immutable local-data snapshot + SHA-256
  -> DiD recipe validation
  -> hash-bound Research-OS-owned R script
  -> trusted local R runner
  -> typed result parser
  -> independent scientific verifier
  -> LocalAnalysisReport + immutable evidence
```

### 4.1 Shared local econometrics kernel

The implementation introduces a small shared kernel intended for later reuse:

- `LocalAnalysisSpec`: method ID, local data reference, column mapping, estimand,
  reference period, inference settings, and resource budget.
- `EconometricsRecipe`: validates method-specific requirements, renders a
  Research-OS-owned script, and parses typed outputs.
- `TrustedLocalRRunner`: runs only the exact generated script through an approved
  absolute `Rscript` executable.
- `LocalAnalysisService`: snapshots inputs, records provenance, executes the
  recipe, verifies outputs, and publishes the report.
- `LocalAnalysisStore`: content-addressed inputs and immutable per-run artifacts.

Only the `did-event-study` recipe is installed in V0.3-A. The kernel must not
contain DiD-specific branching outside the recipe contract.

### 4.2 Trusted R boundary

The runner must:

- require an absolute regular-file `Rscript` path selected in configuration;
- record the executable hash and `R --version` output;
- run with `--vanilla`, an isolated working directory, and a minimal environment;
- ignore user and site startup profiles;
- execute only a script generated from a versioned repository template;
- bind the script SHA-256 to the run manifest before execution;
- reject any free-form command, expression, package installation, or source path;
- use no network connector and contain no network operation in the generated
  script;
- bound elapsed time, output size, and workspace growth without using an absolute
  fixed research deadline.

This is a trusted-script boundary, not an OS sandbox. Because no third-party code
is executed, a full container broker is not required for V0.3-A.

### 4.3 Data boundary

The first useful release supports CSV input only. CSV provides a small, auditable
surface without optional binary readers or package installation.

The service must:

- resolve a regular, non-symlink local file explicitly supplied by the operator;
- copy it into a content-addressed read-only run input area;
- hash the source before and after copying and reject concurrent replacement;
- never write to the source path;
- require explicit names for unit, time, treatment cohort, and outcome columns;
- reject duplicate columns, invalid types, missing identifiers, and non-unique
  unit-time rows before R execution;
- record missing-value handling instead of silently dropping observations.

Future `.dta`, Parquet, or RDS readers use the same snapshot contract and are not
part of this release.

## 5. DiD recipe

The recipe produces two clearly separated result namespaces.

### 5.1 Baseline

- unit and time fixed effects;
- explicitly declared reference period;
- clustered inference at the configured unit level;
- coefficient, standard error, confidence interval, sample size, and fixed-effect
  configuration for every reported event time.

### 5.2 Modern staggered-adoption analysis

- Callaway--Sant'Anna group-time ATT;
- never-treated or not-yet-treated comparison group declared in the spec;
- dynamic/event-study aggregation;
- simultaneous or pointwise confidence interval mode recorded;
- anticipation setting and bootstrap seed recorded;
- explicit unsupported result when the installed R environment cannot provide the
  required estimator.

### 5.3 Required diagnostics

Typed, non-empty evidence is required for:

- cohort and treatment-timing distribution;
- never-treated/not-yet-treated comparison support;
- observations and units by cohort and event time;
- duplicate and missing panel keys;
- pre-treatment coefficients and confidence intervals;
- balance/overlap summary for declared covariates when covariates are supplied;
- estimator and package configuration.

Empty dictionaries, missing estimates, non-finite values, misaligned confidence
intervals, or undeclared observation removal fail verification.

## 6. Outputs and evidence

Every green run publishes:

- immutable input snapshot reference and SHA-256;
- exact analysis specification;
- R executable identity and installed package versions;
- generated script reference and SHA-256;
- stdout/stderr digest and bounded redacted log;
- baseline estimate table;
- group-time ATT table;
- dynamic event-study table and figure;
- diagnostics report;
- independent verification report;
- final `LocalAnalysisReport` containing exact artifact references.

The verifier reopens the current immutable artifacts and independently checks
schema, lineage, finite estimates, interval ordering, expected columns, input and
script hashes, and report completeness. Stored `passed` booleans are never trusted
without recomputation.

## 7. CLI and automation

The user-facing interface is method-neutral:

```text
envresearch econometrics validate --spec local-analysis.yaml --json
envresearch econometrics run --spec local-analysis.yaml --json
envresearch econometrics status --reference-json run-ref.json --json
```

Behavior:

- `validate` is read-only;
- `run` never prompts and never installs dependencies;
- a green run completes automatically;
- invalid data, missing R/package versions, unsupported design, or failed
  verification returns stable JSON with evidence and no routine human gate;
- the external `replication run` command remains fail-closed and cannot be reached
  through the local econometrics commands.

Selecting a local file and column mapping is research input, not a new approval
gate. Human approval remains reserved for external admission, material access or
license exceptions, and promotion to a new benchmark stage.

## 8. Testing and acceptance

V0.3-A is useful-release ready only when:

1. repository-owned staggered-adoption fixtures run through the real configured
   local R boundary when R and pinned packages are available;
2. deterministic fake-runner tests cover environments without R;
3. TWFE and group-time ATT outputs contain finite, aligned estimates and confidence
   intervals;
4. unsupported comparison support, invalid panel keys, missing dependencies, and
   output tampering fail closed;
5. the original local data file remains byte-identical;
6. no test or command downloads packages, accesses Zotero, or executes the JEL
   archive;
7. the complete V0.2/V0.3 offline suite, Ruff, mypy, diff, lock, and changed-file
   format/line gates pass;
8. an independent reviewer finds no Critical or Important issue in the local
   analysis lane;
9. the external replication lane is demonstrably disabled in production.

## 9. Current branch transition

Implementation begins from a recoverable clean checkpoint:

1. preserve the blocked, uncommitted container-runtime experiment in a labelled
   Git stash;
2. return the worktree to committed HEAD without deleting the stash;
3. disable production external-runtime selection and retain its dry proposal,
   contracts, and offline evidence;
4. implement the local econometrics kernel and DiD recipe in a separate commit
   series;
5. run independent review before integration.

No blocked runtime experiment is silently merged or discarded.

## 10. Next method bundle

After this DiD useful release is green, the next delivery is one shared causal
policy bundle rather than three separate infrastructure projects:

- panel fixed effects;
- IV/2SLS;
- RDD.

These recipes reuse the same data snapshot, R runner, artifact store, verification,
CLI, tables, figures, and reporting contracts. Synthetic Control follows because
its donor-pool and placebo diagnostics require a meaningfully different recipe.
Hedonic reuses the FE/IV bundle. Meta-analysis and environmental measurement form
a later non-panel bundle because their data structures and evidence rules differ.

## 11. Governing method waves and reusable data packs

Section 13 of
`plan/2026-08-04-环境经济学与政策研究操作系统-设计规范.md` governs all method
expansion. V0.3-A is the first useful implementation within Wave 1; it does not
replace the approved three-wave roadmap.

Methods will be delivered in coherent capability bundles, not as isolated
infrastructure projects. Method packs and data packs are independent:

- a **method pack** declares estimands, compatible data shapes, assumptions,
  estimators, diagnostics, outputs, and failure rules;
- a **data pack** provides an immutable snapshot plus a typed description of
  units, time, treatment or assignment, outcomes, geography, and provenance;
- a method recipe consumes a compatible data contract and never owns or silently
  downloads a bespoke dataset;
- one dataset may support several methods, and one method may run against many
  approved local or public datasets;
- repository-owned synthetic fixtures support software tests, while a small
  benchmark corpus supports scientific validation;
- real data is acquired only for a concrete research project or benchmark, after
  access, license, provenance, and budget checks—not merely because a method pack
  was installed.

Reusable data-shape contracts will cover experimental assignment, panel treatment
timing, cutoff/running variables, instruments, donor-pool panels,
cross-sectional valuation and choice, spatial/exposure/time-series observations,
and study-level effect sizes. These are contracts rather than mandatory download
jobs.

After V0.3-A, Wave 1 will be completed in a few shared-runtime batches. The first
batch is panel fixed effects + IV/2SLS + RDD. RCT and Synthetic Control then reuse
the causal kernel where their contracts fit; descriptive environmental
measurement and systematic review/Meta-analysis form a non-causal evidence batch.
Wave 2 follows only after Wave 1 is useful and benchmark-clean. Wave 3 remains
gated on stronger calibration, solver verification, and sensitivity-analysis
infrastructure, exactly as required by the master design.
